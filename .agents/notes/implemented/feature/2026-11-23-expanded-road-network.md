# Agent Note: 可行驶路网的支线与共享路口

Status: implemented

## Problem

首版只有一条 7.46 km 的封闭环线，跑完一圈后路线选择单一，山体内部的大片地形也没有可到达的道路。需求是增加长环线、短支线、捷径、S 弯和高低差，主支路之间允许交叉、汇合，并保证每段都可驾驶。最初的七支线版本按工作流边界只导出地图数据，UI 仍显示单环，东西两组内部道路也尚未直连；用户用带箭头的地图明确要求内部节点互通。本轮闭合地图消费链并补跨区道路，同时保持原主线参数、景区直达、车辆与比赛接口。

## Decision

路网以数据驱动方式定义在 `src/world/route.js` 的 `BRANCH_DEFS` 中：主线仍是原来 21 个控制点、7458.6 m 的封闭 Catmull-Rom 环线；另外有 10 条支线，共 10545.7 m。支线用稳定 id 1–10 标识，类型分 `secondary`（宽 9.4 m）与 `trail`（宽 7.4 m），分别对应次级公路和碎石林道。支线端点可以锚定在主线的 `startT` / `endT` 上，也可以落在共享内部节点 `V0`、`V1`、`V2`、`V3`、`V5`、`W0`、`C0` 上；10 处主线岔口与 7 个内部路口共同组成约 18.0 km 的连通路网。

道路 API 保持主线旧接口不变，同时增加按路线取样的 `sampleOn`、`lengthOf`、`widthOf`、`kindOf`、`isClosed`、`nameOf`，并让 `nearest(x, z, preferredRoute)` 返回 `route` 与 `width`。驾驶状态新增 `route`，每帧通过带偏好的最近点查询更新；`mainT` 始终记录最近的主线参数，区域判断与比赛继续消费它。驾驶、相机和巡航按当前路线取样；地图通过 `world.mapPaths` 消费全部道路的中心线。

支线几何用与主线相同的 centripetal Catmull-Rom 采样，间距 3 m。每个主线岔口在需要时插入 38 m 的过渡引导点，把支线方向与主线切向混合，避免出现 4–10 m 半径的掉头弯；实测所有支线最小转弯半径不低于 37 m。

高程分两遍求解，避免道路高度与地形高度互相依赖。第一遍用原始地形高度计算共享节点的统一高程，再为每条支线做“平滑地形—锚点吸附—15% 坡度夹紧”的纵断面；锚点在每次正反向夹紧时都保持固定，所以汇合点不会出现台阶。第二遍地形在 `baseHeight` 之上按支线距离切削路廊，并生成逐支线的细节地形带。主线与支线在平面上会重叠约 50 m，若只锚定单个端点，支线可能比主线高出 1.3 m，形成浮空路和切路时的垂直跳变；因此支线在距主线中心线 `mainWidth / 2 + 1.9 m` 以内直接跟随主线纵断面，再在 10 m 内过渡回自身剖面。共享内部节点则设置 ±14 m 的平坦台地并固定到节点高程，向外 20 m 过渡，使两条支线在整段重叠宽度内都贴合，而不只是在一个采样点等高。

路线选择采用“当前路线优先”的滞回规则：只有车辆离开当前路面的 `width * 0.55` 走廊，且另一条路明显更近时，才切换 `route`；开放支线到达端头时允许并入主线。这样主环线的观光巡航经过岔口时不会被吸到支线上，而从主线主动驶向支线的车辆仍能自然切换。

视觉上，次级公路与碎石林道使用不同宽度、材质和颜色；支线标线在两端各裁掉 34 m，避免画到主线路面上。所有支线的沥青、路肩、标线和碎石面分别合并为 4 个 `BufferGeometry`，路口细节地形也合并为 1 个网格；路面和支路地形共 5 个网格，桥梁使用现有景物实例批次。护栏、路灯、长椅、树木、石块、麦田和建筑按 `branchDistance` 或 `mainJunctions` 让出岔口和路廊。

`main.js` 将 `world.mapPaths` 传给 `createUI`，大地图和小地图遍历同一套真实道路，按 `closed` 决定是否闭合；公路用实线，碎石林道用暖色虚线。移除 UI 自己重新采样主环线的底图路径，区域着色与景区直达保持原有行为。只导出接口未接到地图曾让玩家仍然看见单环，这条生产者—消费者链必须在真实 Canvas 上验收。

内部跨区由三条联络线补齐：`东西横贯线`（893 m，W0—C0—V2）、`中央纵贯线`（1942 m，V1—C0—V3）和`湖谷联络线`（1064 m，镜湖外环入口—V3）。C0 是两条连续道路共享的四向路口，W0 把原西岭盘山线接入中央；移除外环后，十条内部道路仍为一个连通分量。

支线地形同时削坡和填筑，路下地面保持在路面下约 0.2 m。只用 `road.groundHeight` 检查会漏掉悬空，因为该函数在道路上直接返回道路高程；因此测试也检查 `landscape.height` 和实际渲染三角形。粗地形与主路细地形在支路细地形覆盖处让出网格，避免插值后的地面顶穿支路。共享路口内裁掉边线，防止线条横穿交叉口。

湖谷联络线前 62%（约 659 m）采用从镜湖入口缓升至 185 m 的桥面纵断面，保持湖底和河床。桥面板、石护栏和每约 28 m 一组双桥墩复用景物实例批次；桥段不生成贴路的地形带，避免桥下出现悬空地片。

地形高度只查询 80 m 内的支线，细网格覆盖只查询 28–30 m 内的支线。空间索引支持有界最近点搜索，超出半径返回 `null`，驾驶的无限半径最近点语义保持原样。增加网格避让后，重复全图最近点查询使地形生成耗时约 19.9 秒；限定有效半径后同环境约 6.3 秒，附近查询结果与无限半径查询一致。

## Alternatives considered

- **多条独立闭环，各自一套样条与地形**：能最快增加路线数量，但会让区域、比赛和地图各自维护多套参数化，地形切削也会重复计算。最终选择共享主环线与内部节点的单一路网。
- **只按地形高度铺支线，不做显式路口节点**：实现简单，但两条支线汇合处的高程只能碰巧一致，实测会出现米级台阶。最终为每个共享节点先定统一高程，再分别放坡。
- **支线高程只锚定端点**：这是最小改动，但支线与主线并行的 50 m 内会高出主线 1.3 m，车辆切路时会瞬移，视觉上也是一条浮空带。最终增加跟主线纵断面的路口裙边与共享节点台地。
- **在主线路口做水平裙边（固定端点高度）**：当主线本身有纵坡时，裙边末端仍会与主线分离。最终让裙边跟随主线的纵向高程，再过渡回支线剖面。
- **不带偏好的最近路查询**：巡航经过岔口时会被更近的支线中心线吸走，现有环线巡航测试直接失败。最终保留当前路线优先和离开走廊才切换的规则。
- **每条支线单独建网格**：路口细节更直观，但 7 条支线会增加 14 个以上的 draw call。最终按材质合并。
- **只导出 `mapPaths` 等待另一个工作流接入**：原任务划分避免了同文件冲突，但没有形成玩家可见的完整结果。用户本轮要求修正地图后，直接完成地图消费链并保留既有导航交互。
- **只显示原有七条支线**：能解决地图缺线，却仍需要外环连接东西两组道路；补中央横贯和纵贯线才满足内部交叉与跨区互通。
- **南侧沿原地形铺普通路面**：代码更少，但会把道路铺入湖水和河道。采用显式桥段，水体下方保留地形，不填平水面。

## Consequences

路网从七支线版的 14.1 km 增至 18.0 km，新增约 3.9 km 将东西道路、中央十字路口和镜湖连在一起；主线长度、参数化与六个区域的位置保持原义。两种地图与实际道路一致，交叉口允许车辆转入另一条道路。支路路面与地形仍为 5 个合并网格，新增桥梁复用既有实例批次；当前 Chrome 实测中央道路 397 draw calls / 122 万三角形，湖谷桥 314 draw calls / 130 万三角形，连续驾驶约 60 fps。独立 HTML 为 1,366,899 字节，比七支线版增加 2,623 字节（约 0.19%）。

`npm test` 共 28 项通过，新增内部连通、中央路口两种转向、真实路基支撑、桥下净空、有界查询以及渲染三角形不挡路的检查。构建、车辆检查、原有可玩性回归与主线巡航检查全部退出 0；六景区约 60 fps，完整短赛与触屏操作通过。`tools/verify-network.mjs` 在生产预览和独立 HTML 上逐条确认两种 Canvas 中的支路像素可见，并实际驶过中央路口和湖谷桥，覆盖景区直达、竖屏和帧率。`verify-standalone.mjs` 确认离线键盘驾驶且外部请求为零。数值与截图保存在 `shots/network/`。

已知边界：观光巡航只沿当前路线的参数增大方向前进，在内部路线端头换路时需要手动转向；例如 2、5、9、10 均在 V3 汇合。手动驾驶可沿道路任一方向通过，主线环线巡航不受影响。路人车辆仍由交通工作流负责。
